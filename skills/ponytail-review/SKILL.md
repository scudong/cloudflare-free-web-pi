# 精简代码评审

## 何时使用

出现以下任一情况时使用本技能：

- 用户要求评审未提交改动、某个分支、某次提交或 PR。
- 需要判断改动是否过度设计，哪些代码可以直接删掉。
- 需要按严重程度给出可执行的评审意见。
- 用户说「review 一下」「看看这个改动」「有没有更简单的写法」。

不适用：需要运行完整测试套件代替人工判断；对没有上下文的代码片段做风格挑刺。

## 核心立场

像刚接手代码、出故障会被叫去处理的资深开发那样评审。重要性顺序：

1. 正确。
2. 安全。
3. 在预期负载下扛得住。
4. 风险逻辑有测试。
5. 够快。
6. 够精简。

精简仍然重要：多出的每一行以后都要被人读、被测试、被修复。

## 第一步：先理解

- 明确评审对象：未提交改动、暂存区、某个分支、PR 链接或指定文件。用户没说时，默认看未提交改动；没有改动就看最后一次提交。
- 先读 diff，再读它接触的代码：被改函数的调用方、它调用的函数、相关测试、README。
- 工作台文件用 `read_file` 读取，目录用 `list_files` 列出；引用时标注路径和行号。
- 追踪真实数据流：输入从哪里来、存了什么、输出到哪里。
- 改动可能破坏它没碰到的代码。签名、返回值或行为变化时，逐个检查调用方。
- 从 README 和部署配置判断预期负载：单人脚本，还是多用户、多进程并发。明确写出你假设的负载。

## 第二步：按顺序找问题

### 1. 缺陷

- 结果错误、崩溃、漏掉的边界：空值、零、最后一项、舍入、时区。
- 调用方因改动而失效。
- 同一个规则在两个地方实现不一致。
- 只在某个调用点修了，共享函数仍然有问题。

### 2. 风险

- 安全漏洞：注入、弱随机数、硬编码密钥、缺少输入校验。
- 数据丢失：吞掉错误、写入顺序错误、没有事务。
- 权限边界缺失或校验放错层。

### 3. 规模

- 单用户没问题、多用户会坏：先查后写的竞态、每个进程重复做同一件事。
- 只增不减的内存或列表、逐项查询、大输入上的平方级复杂度。
- 本应共享的状态放在进程内。

### 4. 缺失测试

- 有风险的新逻辑没有能在坏掉时失败的测试：分支、解析器、金额、安全、数据写入、缺陷修复。
- 要一个好测试，不要覆盖率数字。
- 测试只验证实现细节，而不是公开行为。

### 5. 速度

- 明显变慢是问题。
- 热循环里的重复计算是建议，不是阻塞项；有些软件确实在乎每一毫秒。

### 6. 精简

- **删除**：死代码、没人用的选项、没人设置的配置、投机性功能。
- **复用**：仓库里已有同样的 helper，指出路径。
- **标准库或平台**：标准库或平台已经能做；为几行代码新增依赖。
- **YAGNI**：只有一个实现的接口、只有一个产品的工厂、只转发调用的包装层。
- **合并**：必须一起改的近似重复代码。
- **拆分**：一个函数做几件不相关的事，难读难测。按职责拆，不按行数拆，不制造只为缩短函数的 helper。

## 第三步：报告前核实

- 每个问题都要有具体场景：「这个输入或这个状态会导致这个错误结果」。没有场景就不算问题。
- 报告前重读相关行，确认调用方真的存在、值真的可能为空、代码真的没人用。
- 判断代码未使用前，全仓搜索，包括测试、fixture、配置、字符串和动态引用。
- 标了 `shortcut:` 或 `ponytail:` 并写明限制的捷径是决策，不是问题；除非预期负载已经越过该限制。
- 提出能工作的最小修复，优先删代码。
- 不添加问题不需要的层、框架或配置。
- 不写风格偏好、不写「可以考虑」、不写模糊担忧。

## 第四步：输出

用简单直白的语言，短句，日常词。技术术语第一次出现时解释。读者可能从没见过这段代码。

开头用两三句话写「这个改动做了什么」，并说明假设的负载。

按三组输出，从最重要到最次要，跳过空组：

- **必须修**：缺陷、安全、数据丢失、在预期负载下会坏。
- **应该修**：有风险但没测试的代码、真实变慢、重复、职责混杂、本不该存在的代码。
- **可以更好**：小的提速、更短的写法。

所有问题统一编号，方便用户说「修 2 和 5」。最多 20 条；省略了较小问题就说明省略了几条。

每条问题包含四部分，每部分一到两句：

1. **是什么**：这段代码在做什么。
2. **问题**：哪个输入或状态会导致什么错误结果。
3. **修复**：最小可行改动，优先删代码。
4. **不修的后果**：谁会受影响，影响是什么。

结尾写：

- **结论**：可以合入，或先修哪几条。
- **精简空间**：可以删掉多少行、去掉多少依赖（如果有）。
- **未检查项**：没读到的部分或无法运行的验证，一行说明。

没发现问题时，写「这个改动做了什么」，然后「看起来没问题，可以合入」，再用一行说明检查了什么。

## 边界

- 只评审，不改代码。
- 不把个人风格偏好写成阻塞项。
- 不因为没有测试就要求补全整个测试套件；只要求覆盖高风险逻辑。
- 不把安全建议降级为「可以考虑」。
