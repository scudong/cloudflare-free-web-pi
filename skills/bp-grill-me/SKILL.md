# 追问式方案评审

## 何时使用

出现以下任一情况时使用本技能：

- 用户要挑战一个方案，验证关键决策是否站得住。
- 计划里还有模糊目标、未验证假设或互相冲突的约束。
- 实施前需要把「大概这样」变成「每个分支都有明确选择」。
- 用户说「追问我」「评审这个方案」「帮我把计划问清楚」。

不适用：已经有明确验收标准的小改动；用户只想直接要一份实现代码。

## 核心原则

1. **事实自己查，决策问用户。** 代码里能查到的不问；需要取舍的必须问。
2. **一次只问一个问题。** 连续抛多个问题会让回答失焦。
3. **每个问题都带推荐答案和理由。** 不让用户从零开始想。
4. **沿着决策树走。** 先解决上游选择，再问依赖它的下游问题。
5. **不确认就不进入实施。** 没达成共识前，不写规格、不拆任务、不改代码。

## 工作流程

### 1. 建立事实底稿

- 从对话、代码和已有文档中提取：目标、约束、现状、已做过的尝试。
- 工作台文件用 `read_file` 读取，目录用 `list_files` 列出；引用时标注路径。
- 把内容分成两类：
  - **事实**：能从代码、文档、接口或数据中验证的内容。
  - **决策**：需要用户权衡优先级、成本、风险或偏好的内容。
- 事实不完整时先补事实，不把猜测包装成问题。

### 2. 画出决策依赖

- 列出必须解决的关键决策，标出先后依赖。
- 优先处理会推翻其他选择的上游决策，例如范围、目标用户、兼容性底线。
- 对每个决策写出：可选方案、各自代价、推荐项、推荐理由。
- 删除不影响结果的伪决策，避免把评审变成问卷。

### 3. 逐个追问

按依赖顺序提问，每次只问一个：

- 先复述当前理解，确认没有听错。
- 给出 2–4 个具体选项，说明代价和风险。
- 明确推荐哪一个，以及为什么。
- 用户回答后，记录结论，指出它推翻了哪些先前假设。
- 如果回答引出新的事实缺口，先查证，再继续。

追问要针对薄弱点，而不是重复确认：

- 这个方案在什么条件下会失败？
- 哪个假设一旦不成立，整个计划就要重做？
- 出问题时如何回滚，谁来发现？
- 这个取舍是否为了省事而牺牲了不可逆的东西？
- 有没有更小的版本能先验证核心假设？

### 4. 处理分歧

- 用户与推荐不一致时，先确认理解了对方的约束，再说明差异的代价。
- 无法当场决定时，标记为开放问题，写明默认方案和触发重新评估的条件。
- 不把「以后再说」当成已解决；开放问题必须有人负责、有时间点。

### 5. 确认门

在以下条件全部满足前，不进入实施、写规格或拆任务：

- 每个关键决策都有明确结论，或明确记为开放问题。
- 开放问题都有默认方案和负责人。
- 用户明确表示理解并同意继续，例如「确认」「可以」「按这个来」。
- 复述一遍最终方案，列出被放弃的选项及原因。

## 文档模式

当方案依赖具体库、框架或外部 API 时，切换到文档模式：

- 列出方案依赖的每个外部行为和版本假设。
- 用 `web_fetch_page` 读取官方文档或 API 参考，优先一手来源。
- 逐条核对：方法签名、参数、版本差异、弃用状态、错误语义。
- 标注「已确认」「已纠正」「仍不确定」三类结果。
- 对仍不确定的点，建议做最小验证实验，而不是继续推理。

不确定时明确说不确定，不要用训练记忆替代文档。

## 输出格式

每轮追问后输出：

- **当前共识**：已经确认的目标、约束和决策。
- **本轮问题**：一个问题，附选项、推荐项和理由。
- **受影响的假设**：这次回答改变了什么。
- **待办验证**：需要查代码、查文档或做实验的事项。

结束时输出：

- **最终方案**：一段话概括。
- **关键决策表**：决策、选择、理由、放弃的选项。
- **开放问题**：问题、默认方案、负责人、复查时间。
- **实施前置条件**：开始动手前还必须满足什么。

## 边界

- 不替用户做需要业务判断的决定。
- 不用连续提问消耗用户耐心；能自己查的一律自己查。
- 不把追问变成挑刺，每个问题都要指向一个真实的取舍。
- 不在确认门前偷偷开始写实现。
