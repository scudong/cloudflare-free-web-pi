# 根因诊断

## 何时使用

出现以下任一情况时使用本技能：

- 缺陷已经确认，但根因不清楚，直接改代码只能碰运气。
- 现象偶发、跨模块，或修复后又在别处复现。
- 用户要求做根因分析（RCA），或明确说「先别改，先查原因」。
- 已有复现步骤，但还没定位到具体模块、函数或配置项。

不适用：需求讨论、纯代码评审、没有可观察现象的猜测式排查。

## 输入

必需：

- 缺陷现象：期望行为与实际行为的差异。
- 复现条件：操作步骤、输入数据、环境（版本、配置、平台）。
- 现有证据：报错、日志、堆栈、截图、监控指标。

可选：

- 最近变更：提交记录、发布版本、配置调整。
- 影响范围：受影响的用户、数据或接口。
- 已知的临时规避方式。

信息不足时先补齐复现条件，不要用推测填补空白。工作台里的文件可以用 `read_file` 读取，目录可以用 `list_files` 列出，读到的内容要标注路径。

## 核心原则

1. **先证据，后结论。** 每个判断都要能指向一条日志、一次复现或一个可证伪的实验。
2. **一次只验证一个变量。** 同时改配置、数据和代码，等于什么都没证明。
3. **区分相关与因果。** 时间上同时发生不等于因果；用对照实验排除。
4. **只确认一个根因再谈修复。** 多个「可能原因」同时存在时，继续隔离。
5. **不改代码。** 本技能只产出诊断结论和修复建议，不执行修复。

## 四个阶段

### 阶段 1：复现

目标：把「有时会坏」变成「按这些步骤必坏」。

- 写出最小复现步骤，去掉与现象无关的操作。
- 记录环境：版本号、配置差异、数据规模、时区、并发量。
- 捕获完整证据：报错原文、堆栈首尾、关键日志时间窗、指标拐点。
- 如果无法稳定复现，记录触发频率和已尝试的条件，转入概率性验证。

完成标准：另一个人按步骤能复现同一现象，或能说清为什么无法稳定复现。

### 阶段 2：隔离

目标：把范围压缩到一个模块、函数、配置项或数据条件。

- 从现象入口向数据流下游逐段验证，确认哪一段的输入正确、输出错误。
- 用二分法缩小范围：注释、开关、最小数据集、单步执行，每次只动一个变量。
- 跨版本问题时，按提交或版本二分；记录每个分界点的可观察结果。
- 跨环境问题时，对比依赖版本、环境变量、网络路径和权限。
- 列出已排除的假设，避免后面重复走回头路。

完成标准：能指出「错误在这个边界内产生」，并给出边界两侧的输入输出证据。

### 阶段 3：假设

目标：把剩余可能性写成可证伪的排序列表。

- 每条假设写成「如果 X 成立，那么做 Y 会观察到 Z」。
- 按解释力和验证成本排序：优先能解释全部现象的假设，其次验证成本低的。
- 为每条假设写出反证条件：出现什么结果就说明它不成立。
- 明确假设依赖的未知信息，不要把它们当成事实。

完成标准：至少两条候选假设，每条都有明确的验证方法和反证条件；或只剩一条且已被证据强力支持。

### 阶段 4：验证

目标：只留下一个被证据确认的根因。

- 逐条执行假设的验证实验，一次一个。
- 记录实验结果，包括不符合预期的结果；不要只留下支持结论的证据。
- 确认根因能解释：现象、触发条件、影响范围，以及为什么之前没被发现。
- 给出修复方向和建议的回归测试点，但不直接改代码。
- 如果所有假设都被推翻，回到阶段 2 扩大隔离范围。

硬门槛：在阶段 4 确认唯一根因之前，不提出修复方案，也不把「可能是」写成结论。

## 输出格式

按以下结构输出，结论先行：

1. **结论**：一句话说清根因；未确认时写「根因未确认」，并列出已排除项。
2. **证据**：复现步骤、关键日志或数据、隔离边界、验证实验及结果。
3. **影响**：受影响的用户、数据、接口和触发条件。
4. **修复建议**：最小改动方向，以及需要补的回归测试。
5. **未验证项**：仍然缺失的信息和下一步实验。

## 边界

- 不为了自圆其说而忽略反例。
- 不把「重启后恢复」当作根因。
- 不在证据不足时承诺修复时间。
- 不修改用户数据或生产配置来验证假设。
