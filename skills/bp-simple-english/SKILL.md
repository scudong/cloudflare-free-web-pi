# 简化技术英语

## 何时使用

出现以下任一情况时使用本技能：

- 写或改 README、操作手册、运行手册、故障报告、发布说明、API 指南。
- 文档面向非母语读者，或需要机器翻译后仍然可读。
- 文本出现长句、同义词轮换、被动语态堆叠或营销腔。
- 用户要求「简化技术英语」「STE」「去 AI 味」「让文档更好读」。

不适用：文学创作、营销文案、需要保留原始措辞的法律文本。

## 核心原则

1. **先分类，再改写。** 每段先判断是操作步骤还是解释说明，两类规则不同。
2. **一个概念只用一个词。** 选定后全篇一致，不为了变化换同义词。
3. **一句一个动作。** 操作步骤按执行顺序写，不把条件和动作混在一起。
4. **保留原文事实。** 代码、标识符、命令行参数、文件路径、错误原文一律不改。
5. **不声称合规。** 本技能参考简化技术英语规则，最终合规判断由作者或标准审核人负责。

## 第一步：分类段落

| 类型 | 用途 | 句式 | 句长上限 |
|---|---|---|---|
| 操作步骤 | 告诉读者做什么 | 祈使句 | 20 词 |
| 解释说明 | 说明是什么、为什么 | 一般现在时、过去时或将来时 | 25 词 |

混合段落拆开：先写一句说明，再列操作步骤。不要在一段里既解释原理又给指令。

## 第二步：统一术语

- 列出反复出现的概念，每个概念选一个词。
- 同义词只保留一个，其余在首次出现时标注「以下统一称为 X」。
- 缩写首次出现时写全称，之后统一用缩写。
- 不为避免重复而换词；技术写作里重复是优点。

## 第三步：改写句子

- 操作步骤用祈使句，开头就是动词：安装、打开、运行、检查。
- 条件放在指令前：如果配置为空，先填默认值，再启动服务。
- 使用主动语态，写清谁做什么。
- 一句话只表达一个判断；用句号断开，不用分号串联。
- 删除填充词：其实、基本上、非常简单、只需要、值得注意的是。
- 删除模糊量词：一些、若干、适当、较快；改成具体数字或条件。
- 避免名词堆叠：超过三个名词修饰同一个词时，拆成短句或加介词。
- 时态保持简单：一般现在时描述行为，一般过去时描述已发生的事。

## 第四步：改写段落

- 一段只讲一个主题。
- 每段最多 6 句；超过就拆分。
- 先给结论或目的，再给步骤或细节。
- 列表项保持平行结构，每项以同类词开头。
- 步骤编号连续，不跳号；每步只做一个动作。
- 警告和限制单独成段，放在受影响步骤之前，不要放在文末。

## 第五步：自检

交付前逐项检查：

- 找出最长的三句，逐词计数；超过上限就拆分。
- 搜索缩写、被动语态、进行时和分号，逐处确认是否必要。
- 检查每个条件句：条件是否在指令之前。
- 检查术语表：同一概念是否出现了两个说法。
- 检查代码块、路径、参数和错误原文是否被改动。
- 检查是否有未经证实的绝对化表述，例如「总是」「绝不」「100%」。
- 检查是否残留营销词和空泛承诺。

## 常见替换

| 不要写 | 改写为 |
|---|---|
| 利用、使用某种能力 | 使用 |
| 为了 | 为了；或直接删掉，改用目的句 |
| 在……之前 | ……之前 |
| 确保 | 确认；或写出具体检查动作 |
| 功能 | 功能；具体到某个操作时写操作名 |
| 应该 | 必须（要求）或删掉（建议） |
| 可能、也许、或许 | 能；或写明触发条件 |
| 进行优化 | 优化；直接写优化了什么 |

替换后必须通读，确认没有改变原意和承诺边界。

## 输出格式

改写任务输出：

1. **改写后的文本**：完整可粘贴版本。
2. **主要改动**：按类别列出，例如拆长句、统一术语、调整条件位置。
3. **未改动项**：代码、路径、参数、引用原文。
4. **仍需作者确认**：涉及事实、数字或承诺边界的地方。

检查任务输出：

- 逐条列出违规位置、问题类型和改写建议。
- 按严重程度排序：可能导致误操作的在前，风格问题在后。

## 边界

- 不编造数字、版本、接口行为或兼容性结论。
- 不把含糊的原意改得更绝对。
- 不为了短句删掉必要的安全警告。
- 不改代码、标识符、命令行参数、文件路径和引用原文。
- 不声称文本已通过简化技术英语认证。
