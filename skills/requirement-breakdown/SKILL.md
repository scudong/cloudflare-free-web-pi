# 需求拆解与验收标准

## 何时使用

出现以下任一情况时使用本技能：

- 用户给出一句话需求或会议结论，要求拆成开发任务。
- 需要在开发前补齐验收标准、边界场景和非功能要求。
- 需要判断一个需求是否足够清晰、能否进入排期。
- 需要把大需求拆成可独立交付的切片。

不适用：替产品负责人决定优先级、估算工时、或把未确认的假设写成确定需求。

## 输入

必需：

- 需求描述：要解决的问题或要交付的能力。
- 目标用户：谁使用、在什么场景使用。

可选：

- 业务目标或衡量指标。
- 现有流程、系统限制和技术约束。
- 截止时间、合规要求、依赖团队。
- 已知的竞品做法或用户反馈。
- 不在本次范围内的内容。

信息不足时，先输出「待确认问题」，不要用假设填满整个方案。

## 拆解原则

1. **问题优先于方案**：先确认要解决的用户问题，再讨论功能。
2. **每个切片可独立交付**：切片之间尽量少共享未完成依赖。
3. **验收标准可观察**：用 Given / When / Then 描述外部可见行为，不写「代码实现正确」。
4. **边界显式化**：空状态、失败、权限、并发、超限都要有定义。
5. **非功能要求单独列**：性能、安全、可用性、兼容性不混在功能描述里。
6. **范围外写清楚**：明确本次不做什么，防止范围蔓延。
7. **开放问题有负责人**：每个未决问题写清找谁确认、何时需要答案。

## 工作流程

1. **复述问题**：用一句话说明「谁在什么场景下遇到什么问题」，让用户确认。
2. **定义目标**：写出一个可衡量的成功指标，区分结果指标和过程指标。
3. **识别角色**：列出主要用户、次要用户和受影响的内部角色。
4. **走主流程**：按用户动作顺序写出正常路径，标出系统响应。
5. **补边界**：逐个检查空、错、慢、多、少、无权限、重复提交。
6. **拆切片**：按用户价值或依赖顺序切成可独立验收的条目。
7. **写验收标准**：每条切片给出 2–5 条 Given / When / Then。
8. **列非功能与依赖**：补充性能、安全、兼容、上线和数据要求。
9. **收敛问题**：把无法自行决定的点整理成开放问题清单。
10. **自检**：确认没有遗漏角色、状态和失败路径。

## 验收标准写法

- **可观察**：写用户能看到的结果、接口返回或数据变化。
- **可判定**：不同人执行同一用例得到同一结论。
- **独立**：一条标准只验证一个行为。
- **带条件**：前置状态、操作和结果都写清楚。
- **避免实现细节**：不写「调用某函数」「新增某张表」，除非这是外部契约。
- **失败也算验收**：错误提示、拒绝、回滚都要有标准。

反例：「登录功能正常。」
正例：「Given 已注册用户，When 输入正确账号密码并提交，Then 进入工作台且会话保持 7 天。」

反例：「性能良好。」
正例：「在 1000 条记录、单用户条件下，列表首屏响应时间不超过 800 毫秒。」

## 切片规则

- 每个切片能独立上线或独立验收；不能独立上线时说明依赖。
- 优先切出用户可感知的价值，而不是按技术层切。
- 共享基础能力先做成最小可用版本，再叠加场景。
- 单个切片建议不超过 3 天；超过则继续拆。
- 切片之间避免循环依赖；无法避免时明确先后顺序。

## 边界场景清单

- 空列表、首次使用、无历史数据。
- 字段缺失、格式错误、超长输入。
- 未登录、无权限、角色切换。
- 网络失败、服务超时、部分成功。
- 重复点击、并发修改、顺序错乱。
- 数据量超过一页、超过上限、导出大文件。
- 删除后恢复、撤销、回滚。
- 时区、语言、金额精度和单位差异。

## 质量检查清单

- [ ] 用户问题能用一句话说清。
- [ ] 成功标准可衡量。
- [ ] 每个用户故事都有验收标准。
- [ ] 验收标准使用 Given / When / Then 且可观察。
- [ ] 空、错、慢、多、少、无权限六类边界已覆盖。
- [ ] 非功能要求单独列出。
- [ ] 范围外内容明确。
- [ ] 开放问题都有负责人和截止时间。
- [ ] 切片可独立交付或有明确依赖顺序。

## 边界

- 不替产品负责人决定优先级和商业取舍。
- 不估算具体工时，只给相对顺序和依赖。
- 不把技术方案当成需求本身。
- 涉及合规、隐私或支付时，提示需要对应负责人确认。
