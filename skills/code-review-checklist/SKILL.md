# 代码评审清单

## 何时使用

出现以下任一情况时使用本技能：

- 用户给出 diff、PR 描述或代码片段，要求评审。
- 需要在合并前做一次系统性风险检查。
- 用户要求把评审意见按阻塞程度排序。
- 需要检查改动是否破坏既有接口或数据。

不适用：代替用户运行完整测试、对没有上下文的大段代码做风格挑刺、或把个人偏好写成阻塞项。

## 输入

必需：

- 变更内容：diff、PR 链接或改动后的文件。
- 变更目的：修复什么问题、实现什么需求。

可选：

- 相关调用方、接口文档、数据模型。
- 测试结果和复现步骤。
- 目标分支和兼容性要求。
- 团队规范或已有代码风格。

缺少变更目的时，先要求一句话说明；仍无法确认时，把假设写在评审开头。

## 评审顺序

按风险从高到低检查，不要从命名和格式开始：

1. **正确性**：输入、输出、状态转换是否符合目的。
2. **边界与错误**：空值、零值、超长、超时、重试、部分失败。
3. **并发与顺序**：共享状态、竞态、重复提交、幂等。
4. **数据与兼容**：迁移、回滚、旧数据、接口字段变化。
5. **安全**：鉴权、越权、注入、敏感信息、日志泄露。
6. **性能**：额外请求、全表扫描、无界循环、内存增长。
7. **测试**：是否覆盖新行为、边界和失败路径。
8. **可维护性**：命名、分层、重复逻辑、死代码。

## 工作流程

1. **读目的**：用一句话复述这次改动要解决的问题。复述不出就停下来问。
2. **划范围**：列出改动文件和受影响调用方，标出不在 diff 里但会被影响的模块。
3. **走主路径**：按正常输入推演一遍，确认输出符合目的。
4. **走失败路径**：逐个检查空值、异常、超时、重试和回滚。
5. **查契约**：确认函数签名、接口字段、数据库列和错误码是否向后兼容。
6. **查测试**：确认测试能覆盖新增分支，且不是只验证「不报错」。
7. **写意见**：每条给出位置、问题、影响、建议；按严重程度排序。
8. **复核**：删掉纯风格偏好，合并重复意见，确认没有编造行号。

## 严重程度

- **Blocker**：会导致数据错误、安全问题、线上故障或契约破坏，必须合并前修。
- **Major**：在常见场景下会产生错误行为或明显维护风险，应合并前修。
- **Minor**：边界场景或可维护性问题，可排期修。
- **Nit**：命名、格式、注释等偏好，不阻塞合并。
- **Question**：需要作者解释，不预设对错。

## 输出格式

```markdown
# 代码评审：<PR 标题或变更摘要>

## 结论

<可合并 / 修复后合并 / 需要重新设计>。一句话说明主要原因。

## 阻塞问题

### [Blocker] <问题标题>

- 位置：`<文件>:<行号或函数名>`
- 问题：<具体行为，不写「可能有问题」。>
- 影响：<什么场景会出错，后果是什么。>
- 建议：<最小修复方向，必要时给伪代码。>

## 重要问题

### [Major] <问题标题>

- 位置：`<文件>:<行号或函数名>`
- 问题：<...>
- 影响：<...>
- 建议：<...>

## 次要问题

- **[Minor]** `<位置>`：<问题>；建议 <修改>。
- **[Nit]** `<位置>`：<问题>；建议 <修改>。

## 测试缺口

- <缺失的测试场景>：<为什么重要>；建议补 <用例>。

## 做得好的地方

- <具体说明一处值得保留的设计或实现。>

## 待确认

- <需要作者回答的问题，附上你的假设。>
```

## 检查清单

### 正确性

- [ ] 正常输入得到预期输出。
- [ ] 条件分支覆盖了所有枚举值。
- [ ] 循环有明确终止条件。
- [ ] 状态转换没有遗漏或非法跳转。
- [ ] 时间、时区、金额、精度处理一致。

### 边界与错误

- [ ] 空数组、空字符串、零值和缺失字段有定义。
- [ ] 超长输入、分页边界和最大数量有限制。
- [ ] 外部调用失败会返回可理解的错误。
- [ ] 重试不会造成重复写入。
- [ ] 部分成功时有清理或补偿。

### 并发与数据

- [ ] 共享状态有同步或串行化保证。
- [ ] 同一请求重复执行结果一致。
- [ ] 数据库迁移可回滚，旧数据可读。
- [ ] 删除或重命名字段保留了兼容期。
- [ ] 事务边界覆盖了相关写入。

### 安全

- [ ] 每个入口都校验身份和权限。
- [ ] 用户输入不会直接拼进查询或命令。
- [ ] 错误信息不泄露密钥、路径或内部细节。
- [ ] 日志不记录完整凭证和个人敏感信息。
- [ ] 外部 URL 有协议和主机校验。

### 性能与测试

- [ ] 没有在循环里发起无界网络或数据库调用。
- [ ] 新增查询有合适索引或数量上限。
- [ ] 测试覆盖新增行为，而不只是「不抛错」。
- [ ] 失败路径有测试。
- [ ] 测试不依赖执行顺序或真实外部服务。

## 写评审意见的规则

- 先给结论，再给证据；不要用「感觉」「可能」代替具体场景。
- 每条意见只对应一个问题，避免一条里塞五个建议。
- 引用代码时只引用 diff 中真实存在的片段。
- 对不确定的判断标成 Question，并写出你的假设。
- 不要求作者重写整个模块，优先给最小可行修复。
- 不把格式化、命名偏好升级为 Blocker。
- 同一问题出现多次时，在第一条写全，其余标「同上」。

## 边界

- 不代替作者执行测试或部署。
- 不评审与本次目的无关的历史代码，除非它直接放大本次风险。
- 不对作者能力做评价，只讨论代码和行为。
- 涉及安全漏洞时，不在公开评论里贴可利用细节，提示私下同步。
